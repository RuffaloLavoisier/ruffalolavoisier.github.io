OTT for Media Center

공개 범위에 대하여. 이 글은 특정 서비스를 가리키지 않는다. 호스트 이름, 엔드포인트 경로, 파라미터 이름, 토큰·서명 형식, 난독화의 구체적인 절차는 모두 뺐거나 <…> 자리표시자로 바꿨다. 코드도 식별자를 일반적인 이름으로 고쳤다. 남긴 것은 어느 스트리밍 클라이언트에나 적용되는 구조와 디버깅 방법이다. 그대로 따라 해서 무언가를 재현할 수 있는 글이 아니라는 점을 먼저 밝혀 둔다. 또한 개인적인 학문 연구와 연구용으로 진행한 것으로, 상업적 목적이나 특정 서비스의 이용 약관을 위반하는 행위에 대한 안내가 아님을 명시한다. 해당 글을 읽고 다른 불법적인 행위를 할 경우 해당 책임은 전적으로 독자에게 있음을 밝힌다. 그리고 무엇보다 이 글은 OTT 서비스의 보호 절차를 우회하는 방법을 안내하지 않는다. 단지, OTT 서비스가 제공하는 영상 소스를 재생기에 물리기 위해 거치는 절차를 분석하고, 그 과정에서 발생한 문제를 디버깅한 기록을 정리한 것이다.

서막

OTT 서비스를 원활하게 보기 위하여 OTT 앱을 만들어서 쓰고있다. 그러다 어느 날부터 어떤 영상을 눌러도 같은 알림만 떴다.

1

이 링크에서 영상을 찾지 못했습니다. 회차가 포함된 영상 링크를 확인해 주세요.

처음 든 생각은 두 가지였다. 키 난독화가 바뀌었거나, 조각 암호화 방식이 바뀌었거나. 둘 다 “복호화가 깨졌다”는 가설이고, 가장 공들인 부분이라 가장 먼저 의심했다.

메시지가 나오는 줄부터 찾는다

디코더를 열기 전에 문구로 검색부터 했다. 메시지는 영상 주소를 조회하는 함수 안에서 나오고 있었다.

이 한 번의 검색으로 두 가지가 정리됐다.

  • 이 단계는 재생목록을 받기도 전이다. 키 복원과 AES는 한참 뒤의 일이다. 복호화가 깨졌다면 다른 메시지가 떴어야 한다. 가설은 열어 보기도 전에 틀렸다.
  • 반대로 이 except 하나가 너무 많은 경우를 같은 문구로 뭉뚱그리고 있었다. 서버 오류, 응답 형식 변경, 필드 누락이 전부 같은 메시지다. 과거의 내가 만든 함정이다.

문구만으로는 원인을 가를 수 없으니 응답을 직접 봐야 했다.

원인이 한 줄로 드러났다. 예전에는 재생목록 주소가 바로 들어 있던 필드가 빈 문자열이 됐다. 기존 코드는 이 값이 비면 곧바로 “찾지 못했습니다”를 던지니, 서버가 응답을 바꾼 순간부터 모든 영상이 실패한 것은 당연했다.

대신 클라이언트가 열어 볼 수 없는 꾸러미가 하나 온다. “주소를 바로 알려 주지 않고, 절차를 밟아야 준다”로 설계가 바뀐 것이다.

브라우저는 이 꾸러미로 무엇을 하는가

개발자 도구의 Network 탭에서 재생 버튼을 누른 뒤의 요청을 순서대로 따라갔다. 구조는 세 단계였다.

1
2
3

① 영상 정보 조회      → 불투명한 꾸러미 (주소 없음)
② 꾸러미를 되돌려 보냄 → 서명된 플레이어 페이지 주소 + 만료 시각
③ 플레이어 페이지 요청 → HTML 안의 설정 객체에 토큰이 붙은 재생목록 주소

각 단계를 직접 호출해 가정을 확인했다. ②의 본문 형식은 받은 꾸러미를 손대지 않고 그대로 직렬화해 보내는 것으로 한 번에 통과했다. ③의 응답 HTML에는 스크립트 태그 안에 설정 객체가 있었고, 거기서 재생목록 주소를 찾았다.

두 가지를 기록해 뒀다.

  • 서명된 주소도, 재생목록 토큰도 수명이 몇 분이다.
  • 서버는 단계마다 다른 호스트를 쓴다. 사이트, 플레이어, 재생목록·키 서버, 조각 서버가 갈라져 있고 호스트마다 기대하는 요청 헤더가 다르다.

그런데 재생목록이 403

토큰이 붙은 주소를 얻었으니 끝난 줄 알았다. 그대로 요청하니 403 Forbidden이 돌아왔다. 익숙한 용의자부터 하나씩 시험하고 표로 남겼다.

시도결과
Referer 없음403
Referer = 플레이어 도메인403
위 + Origin = 플레이어 도메인403
예전 플레이어 도메인을 Referer로403

방금 발급받은 토큰이고 서명도 맞는데 거절된다. 표를 채우고 나니 분명해졌다. 이건 헤더 문제가 아니다. 헤더 조합을 더 늘려 봐야 시간만 쓴다.

요청이 “플레이어가 보낸 것처럼” 보이지 않는다면, 무엇이 플레이어다운지는 플레이어 스크립트가 알고 있다.

플레이어 스크립트 읽기

플레이어 페이지가 불러오는 스크립트를 받아 텍스트로 읽었다. 압축된 수십 KB짜리 파일을 처음부터 읽을 수는 없으니 키워드로 훑었다. 요청을 만드는 지점(fetch(, XHR 설정 훅, 소스를 로더에 넘기는 호출)과 설정 객체의 필드 이름이 출발점이다.

막다른 길이 하나 있었다. 설정 객체에 “사전 등록”처럼 보이는 항목이 있고, 그 값을 별도 주소로 POST하는 함수가 있었다. 이걸 건너뛰어서 403이 나는 줄 알았다. 하지만 호출 지점을 따라가 보니 특정 브라우저의 네이티브 재생 경로에서만 쓰였다. 내가 재현하려는 일반 경로와는 무관했다. 그럴듯한 단서라고 바로 구현하지 않고 호출 지점까지 확인한 덕에 헛수고를 줄였다.

진짜 단서는 모든 재생 경로가 공통으로 거치는 작은 함수였다. 플레이어는 일부 요청에 한해 주소에 부가 값을 하나 덧붙이고 있었다. 서버가 내려준 값이 아니라 클라이언트가 스스로 만드는 값이고, 서버는 그 값의 유무로 “플레이어에서 나온 요청인지”를 가늠하는 것으로 보였다. 그 값이 무엇이고 어떤 형식인지는 적지 않는다.

가설을 바로 실험했다. 같은 주소에 그 값만 더했다.

1
2

(헤더만 조정)              → 403
(헤더 + 플레이어와 같은 값)  → 200  application/vnd.apple.mpegurl

재생목록이 열렸다. 범인은 Referer가 아니었다.

복호화는 한 줄도 바뀌지 않았다

재생목록이 열렸으니 처음 가설을 닫을 차례다. 기존 코드 경로에 그대로 태웠다.

1
2
3

재생목록 파싱   → 조각 수천 개, 키 1개
키 복원        → 16바이트 (기존 디코더 그대로)
첫 조각 복호화  → 188바이트 패킷마다 0x47, 정상

키 복원과 AES 복호화는 한 줄도 고칠 필요가 없었다. 바뀐 것은 암호가 아니라 주소를 얻는 절차였다. 가장 먼저 의심했던 곳이 유일하게 멀쩡한 곳이었다.

서버가 가리키는 주소를 그대로 믿지 않는다

②의 응답은 “이 플레이어 주소로 가라”고 알려 준다. 코드는 그 주소의 스킴, 호스트, 포트, 경로 형식이 기대한 것과 같은지 확인하고, 다르면 요청하지 않는다.

1

4

if (player.scheme != "https" or player.hostname != expected.hostname
        or player.port not in (None, 443) or player.username or player.password
        or not re.fullmatch(r"/<…>/[0-9A-Za-z_-]+", player.path)):
    raise SiteError("플레이어 주소가 예상과 다릅니다. 플레이어 도메인이 바뀌었을 수 있습니다.")

응답이 가리키는 임의의 호스트로 서명 값을 들고 가지 않기 위해서다. 도메인이 실제로 바뀌면 깨지지만, 그때는 원인이 메시지에 그대로 보인다. 조용히 엉뚱한 곳으로 가는 것보다 낫다.

같은 원칙을 전송 계층 전체에 적용했다. HTTPS만 허용하고, 주소에 사용자 정보나 제어 문자가 있으면 거부하고, 리다이렉트 뒤의 최종 주소를 다시 검증하고, 응답 크기에 요청별 상한을 둔다.

HTML 속 JSON은 정규식으로 자르지 않는다

설정 객체는 <script> 안에 window.<설정> = {...}; 형태로 들어 있다. 중괄호를 정규식으로 맞추려 들면 문자열 안의 } 하나에 무너진다. 표준 라이브러리에 딱 맞는 도구가 있다.

def parse_embedded_config(page_html, name):
    marker = page_html.find(name)
    equals = page_html.find("=", marker) if marker >= 0 else -1
    if equals < 0:
        raise ValueError("no config")
    start = equals + 1
    while start < len(page_html) and page_html[start].isspace():
        start += 1
    config, _ = json.JSONDecoder().raw_decode(page_html, start)   # 객체 하나만 정확히 읽는다
    if not isinstance(config, dict):
        raise ValueError("config is not an object")
    return config

raw_decode는 지정한 위치에서 시작하는 JSON 값 하나를 읽고 끝난 위치를 돌려준다. 뒤에 ;나 다른 스크립트가 붙어 있어도 상관없다.

읽는 값은 필요한 키 하나뿐이다. 같은 객체에 광고 정보나 다른 필드가 있어도 읽지 않는다. 응답에 딸려 오는 자유 텍스트 필드도 마찬가지로, 쓰지 않을 값은 파싱 직후에 걸러 내고 필요한 키만 명시적으로 꺼낸다. 서버가 보내는 문자열은 입력이지 지시가 아니다.

수명이 짧은 토큰은 쓰는 순간에 받는다

이 변경으로 다운로드 대기열이 구조적으로 깨졌다. 원래는 회차 여러 개를 대기열에 넣을 때 주소를 미리 받아 두고 순서대로 내려받았다. 토큰 수명이 몇 분이면 두 번째 작업부터는 차례가 왔을 때 이미 만료돼 있다.

책임을 옮겼다. 플러그인은 회차 페이지 주소만 서비스에 넘기고, 작업이 시작되는 시점에 주소를 조회한다.

이 알고리즘은 유튜브 영상 소스를 추출하는 youtube-dl과 비슷하다. 영상 주소를 미리 받는 것이 아니라, 다운로드가 시작될 때 요청한다. 토큰이 짧아도 문제없다.
